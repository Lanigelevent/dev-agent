# AB-16 rail 校验注册表对照审计（r215，2026-11-27）

> 对照源：Guardrails AI 7.6k Apache（可组合校验器 + 校验失败重试生成 + on_fail 动作）。
> 审计对象：五道闸输出侧（fix-apply.py 五道闸 + approve 链 + MCP run 退出码语义）。
> 总监批准背景：2026-11-27 阶段三全量批准。

## 一、概念映射

| Guardrails AI 概念 | dev-agent 五道闸现状 | 判定 |
|---|---|---|
| 可组合校验器（validators 按需组装管道） | 五道闸=**固定 5 道**（批准书/工作树/HEAD/apply 预检/行为回归），非可组装 | **结构性不同**——闸面是工作流闸（治理序列），非输出校验管道 |
| on_fail=EXCEPTION（抛错停止） | 闸 1–4 失败 → rc=2（前置不满足，不落盘直接拒） | **已对齐** |
| on_fail=REEXCEPTION（清理后重抛） | 闸五失败 → 自动回滚 ROLLED_BACK 落 apply-log（含清理，语义更强） | **已对齐** |
| on_fail=HUMAN | NEED_HUMAN 升级链（human-gate 五类触发；MCP run rc=1 不算错误；L1→L2→L3 值班链） | **已对齐** |
| on_fail=FIX（校验失败自动修复重试） | **无**——闸五失败不原包重试 | **有意排除**：同一产物目录重试会抹掉上一条 ROLLED_BACK（fix-apply L329 防双记）；修复重试走「批准书作废重审」（补丁任何变动即重走闸 1→闸 2），治理更强 |
| 校验失败→重试生成（regenerate） | **无** | **有意排除**：批准书 sha256 绑定补丁包，变动即作废重审——与「重试生成」是同一需求的两种治理哲学，我们选更强的 |

## 二、on_fail 动作面盘点（现有标准化）

| 失败点 | 动作 | 载体 | 退出码 |
|---|---|---|---|
| 闸 1–4 前置不满足 | 拒绝不落盘 | rc=2 + 错误描述 | 2 |
| 闸五行为回归失败 | 自动回滚 + 台账采集 | ROLLED_BACK → apply-log.json → retro-ledger | 1 |
| 审核人 REJECTED | 退回返工 | verdict=REJECTED + reasons | 0（结论不算错） |
| 运行未收敛/预算超限 | 转人工 | NEED_HUMAN（MCP run rc=1） | 1（不算错误） |

on_fail 动作面**已是标准化的三态语义**（rc 0/1/2 + 结论态 REJECTED/ROLLED_BACK/NEED_HUMAN），四类失败点全有明确载体与台账去向。

## 三、结论

**AB-16 终局：已对齐（2 面有意排除，治理哲学更强）**——on_fail 动作面已标准化（rc 三态 + 结论三态 + 台账去向明确）；Guardrails 的「FIX/重试生成」与我们的「批准书作废重审」是同一需求（失败后的处置）的两种哲学，我们选择不自动重试（防双记 + 两人规则）。rail 注册表（可组合校验器）与工作流闸结构性不同，不采纳。**不吸收，无需改动。**
